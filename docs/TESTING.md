Run everything yourself: `test.bat` on Windows, or

```bash
python -m pytest                        # backend, from the repo root (about 8 minutes: password hashing is deliberately slow). Do not start it within a few minutes of midnight IST
cd frontend && npm test                 # frontend
cd frontend && npx tsc --noEmit         # strict type check
# browser checks: start the app on a THROW-AWAY database first (see the header of scripts/e2e_browser.py), then
SWARA_E2E_PASSWORD=... python scripts/e2e_browser.py http://localhost:8000 --db path/to/that.db --owner-email you@example.com --skip-controls
SWARA_E2E_PASSWORD=... python scripts/e2e_browser.py http://localhost:8000 --db path/to/that.db --owner-email you@example.com --only-controls   # slow: one page load per button
python scripts/evaluate_nlu.py --tag mine --failures
python scripts/evaluate_branded.py
python scripts/build_evaluation_summary.py     # the numbers behind the AI performance screen and the report (about 16 s)
python scripts/build_verification_summary.py   # counts the saved logs into the test record
python3 scripts/build_report.py --files        # needs matplotlib, pandoc, Playwright; not app dependencies
python scripts/take_screenshots.py --email you@example.com --signup   # needs SWARA_SHOT_PASSWORD, the app running, and: pip install playwright && playwright install chromium
```

The latest backend run ended with five warnings: Starlette's deprecation notice about its `TestClient` using `httpx`, which comes from the library, not this code (always), and four `ResourceWarning: unclosed database` (see the table above: a connection left to the garbage collector; they fail nothing and the cause was not traced to a line; earlier runs printed none or one). The frontend run prints no React warnings; the only error traces in its log ("Kaboom", "first render fails") are the `ErrorBoundary` tests throwing on purpose.

The browser run renames the shop and puts the name back; the app keeps the shop name in `.env`, so that run leaves a one-line `.env` (`STORE_NAME=...`) in the project folder. It holds no key, git ignores it and the release ZIP leaves it out; delete it if you want a pristine folder.

The browser scripts are the only checks that touch a real browser, a real cookie jar, a real server process and a real SQLite file together. They create a fresh database, never use the developer's own data, and the expired-session check works by moving the session's expiry into the past in that throw-away database.

## Versions that were tested

The backend requirements are version *ranges*, not a lock file, so a fresh install may resolve newer releases than these. If something behaves differently, these are the versions the 1,103 tests ran on:

Python 3.13.18 · FastAPI 0.162.2 · Starlette 1.10.0 · Uvicorn 0.54.0 · SQLAlchemy 2.1.8 · Pydantic 2.14.3 · pydantic-settings 2.16.2 · httpx 0.28.1 · python-multipart 0.0.33 · websockets 17.4 · NumPy 2.5.4 · pytest 9.2.0 · pytest-asyncio 1.4.1 · pytest-cov 7.1.0.

Frontend (locked by `package-lock.json`): Node 22.23.4 / npm 10.9.9 · React 18.3 · react-router-dom 7.18.5 · Recharts 3.10 · Vite 7.3.8 · Vitest 4.1.12 · jsdom 31 · TypeScript 5.9. ## What the tests prove, and what they do not

**They prove** the logic: parsing, money, stock, dialogue, security rules, the shape of every request we send to Gnani, that we survive every error shape Gnani documents, that analytics come from database rows and follow their stated rules, and that each page handles loading, error, empty and loaded states.

**They do not prove**

- that Gnani's live service behaves as its documentation says (the simulator is built from that documentation, so a documentation error would be copied into both the code and the test);
- real microphone capture and the AudioWorklet in a browser (the resampler and WAV encoder are unit-tested; capture is not);
- Windows behaviour of the `.bat` scripts;
- Prisma accuracy on real speech;
- layout in any browser other than headless Chromium, or accessibility with a real screen reader (see [DESIGN.md](DESIGN.md));
- PostgreSQL behaviour (only SQLite has been run);
- e-mail through a real provider: STARTTLS, SSL and authenticated SMTP login were never run, only a plain local test server (so the reset and verification e-mails are untested in the real world);
- the app behind https and a real reverse proxy (the https cookie and header rules are tested in code, not with a certificate and a proxy);
- more than one server process (the lock-out and rate-limit counters live in one process's memory, see [SECURITY.md](SECURITY.md));
- load, or any measured page-speed or Lighthouse score (none was run, so none is claimed);
- **anything about Razorpay itself** (2.7.0): every Razorpay test runs against a stand-in written from the public documentation as remembered while building, so a wrong field name or endpoint would be copied into both the code and the test. Checkout in a browser, real webhook delivery, real refunds, the Razorpay UPI QR and live mode were never run; see [PAYMENT_TESTING.md](PAYMENT_TESTING.md) and the test-mode checklist in [RAZORPAY_SETUP.md](RAZORPAY_SETUP.md);
- a real phone scanning the UPI QR, or a real bank confirming it;
- sign-in with Google or any other provider: it is not built.
