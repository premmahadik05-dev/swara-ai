# Verification report: SWARA AI 2.7.0

What was run for this release, what it showed, and what was **not** run. Nothing here is estimated: every number comes from a log in
[`test-results/`](test-results) or a result file in [`../eval/results/`](../eval/results), written by the command shown. Longer background: [TESTING.md](TESTING.md). The languages themselves: [LANGUAGES.md](LANGUAGES.md). The same record, counted from the logs by `scripts/build_verification_summary.py`, is the "Test and verification record" table on the app's **AI performance** screen and Table 10 of the [project report](PROJECT_REPORT.md).

**Environment (all runs):** Linux, 2 CPU cores, Python 3.13.18, Node 22.23.4 / npm 10.9.9, Chromium driven by Playwright 1.63.0, 10 and 11 Nov 2026 (the 2.7.0 runs on 11 Nov).
**No run was made on Windows, against live Gnani, against Razorpay, or with a microphone.**

> **2.7.0 adds payments, refunds and invoices and leaves the voice path as it was (every voice-path test from 2.6.0 passes unchanged).** What the release needed verified is in rows 1 to 5, 20 and 27 to 30 below, and in
> [PAYMENT_TESTING.md](PAYMENT_TESTING.md). **Every Razorpay response in every test is simulated**: no payment, refund or webhook went through Razorpay, no live key was used
> and nothing about Razorpay's own servers was verified (section 3). The step-by-step test-mode check to run on your machine, with your own test keys, is in [RAZORPAY_SETUP.md](RAZORPAY_SETUP.md).
>
> **Earlier, 2.6.0 changed how a spoken order reaches the screen, adds an owner-only Voice diagnostics page and Analytics measures, and adds no language.** The language status below is
> unchanged from 2.3.0. What the release needed verified is in rows 1 to 5, 14, 20 and 22 to 26 below. **Every figure about the voice path comes from a simulated Gnani**
> (a local stand-in with stated delays, or a mock transport in the tests): no live call, no real speech and no microphone were involved, so no speech latency or accuracy was measured.
>
> **Headline.** The Order desk offers the ten languages Gnani documents for Prisma v2.5
> (speech to text) and Timbre v2.5 (text to speech), plus Hinglish. **Not one of the eleven has been run against live Gnani**: this environment has no
> Gnani key and no route to Gnani. Every Gnani response in every automated test is simulated. So the honest status of **all eleven languages
> is "not verified live"**, for speech recognition and for speech synthesis alike, and **no speech accuracy or speech latency was measured anywhere**. The app says so on screen, and the one-command check that settles it
> on your machine is `verify_gnani.bat`.

What the table does **not** say, so you do not have to infer it:

- It does not say Prisma recognises any of these languages well, or at all, from a real voice. Nobody has spoken any of them to this build.
- It does not say Timbre's voice for a language sounds right, or that the default voice is the best choice. Each default is one of Gnani's documented voices for that language; none was listened to. You can change it in Settings → Languages and voices.
- It does not say the seven added packs use the words a shopkeeper would use. They were written for this release and agree with their author's tests.
- Auto-detect is **not offered** on Prisma v2.5 (Gnani documents exactly one language per request there). The app refuses `auto` and `mixed` with a clear
  error instead of guessing; 2.2.0 used to send them as Gujarati. On Prisma v3.0 they are sent as documented, untested live.
- Inverse text normalisation (digits and formatting) is requested only for Hindi and English, the two languages for which Gnani documents it on v2.5.
- There is no fallback language and no fallback provider anywhere: if Gnani refuses a language or a voice, the error is shown and nothing else is tried.

**How to turn "not verified" into a result.** Put your key in `.env`, run `verify_gnani.bat` (or `python scripts/verify_gnani.py`). It makes about 33 real
calls: for each language a Timbre call (`tts`), a Prisma call on a generated tone to check the language code is accepted (`stt_code`), a Prisma call on
Timbre's own speech for that language (`stt_loopback`), and, if you put a recording at `eval/samples/<key>.wav`, a Prisma call on a real voice
(`stt_human`). The result is written to `eval/results/live_verification.json`, which the Order desk reads; a run made with a simulated client never
writes that file, and a file marked simulated can never show as a pass. A loopback pass proves the language code and the voice work together. It does **not**
prove Prisma understands a shopkeeper's accent; only `stt_human` with a real recording says anything about that.

## 4. Simulated, generated or authored, as opposed to real

- **Razorpay responses in all tests are simulated** (`FakeRazorpay` in `backend/tests/payment_helpers.py`). The keys in the tests are made-up placeholders with the right prefix, not credentials, and the UPI ID in the payment screenshots is an invented example. Every payment, refund and invoice figure in the screenshots and in the browser runs is from a handful of payments made on a throw-away database.
- **Gnani responses in all tests are simulated.** No latency, accuracy or word-error figure in the repository comes from a Gnani call unless a script
  in `scripts/` made it on your machine. The documented codes and voices were read from Gnani's public documentation; a copy lives in the tests.
- **Every accuracy figure on the AI performance page and in the report is for typed text**: sentences written by the project author (128 hand-written, 160 templated, 70 authored for the added languages) and 300 templated sentences built from catalogue products the parser was not tuned on. They were not collected from shopkeepers and no speech is involved.
- **The language packs for Marathi, Bengali, Tamil, Telugu, Kannada, Malayalam and Punjabi are authored text**, unit-tested against their author's
  expectations. They are labelled "New in 2.3" on the Order desk. The four earlier languages' sentences have a longer history of use.
- **The branded-product figures are on templated text** built from product names, with no speech in the loop. They are an optimistic ceiling.
  The "wrong product" answers were read one by one and classified in the report; that classification is the author's reading, not an independent label.
- **Demo data is generated and labelled "Demo"**: orders, customers, demo prices and the held-out test sentences. The 5,325-product catalogue is
  real public data (Open Food Facts, ODbL) and **contains no prices**. The demo tables and charts in the report come from `scripts/demo_activity.py`, which placed a few typed orders, two restocks and a cancellation through the real API on a throw-away database (with `--payments`, also four payments, one part refund and an invoice, none of them through Razorpay).
- **Screenshots** in `docs/screenshots` are real captures of the running app (2.6.0 for 02, 04, 18, 38 and 39; 2.5.0 or 2.4.0 for the rest, see row 20) (a throw-away owner account, generated demo data), Chromium
  only. The product pictures on the landing page are captures from an earlier run, converted to WebP, and the page labels them "generated demo data".
- **The landing page's demonstration** posts typed text to the real `POST /api/text/parse`; it involves no microphone and no Gnani call, and says so.
  The product showcase's sample sentences are authored text, not recordings.

## 5. Found and fixed

**In 2.7.0:**

- **The payment window flashed its "choose a way" screen while it reopened an unfinished payment.** Found by the real-browser run: the order and the payment were loaded one after the other. They are now set together, and a test, checked by breaking the code on purpose, fails if the flash returns.
- **The payment window accepted a cash amount the server would refuse** (more than twenty times the bill plus 1,000 rupees, a typing slip). The window now applies the same limit before sending; the server still refuses it too.
- **Wording faults found by reading the pages:** "not verified" shown twice on a hand-confirmed UPI payment, an "Unverified" badge on cash payments, the owner shown as "Staff" on the invoice, and a "test mode" note with no Razorpay keys set. Each now has a test.
- **The test that keeps Razorpay secret names out of the frontend failed on legitimate words**, such as the public key id the browser needs. It was narrowed to secrets and credential values, and a second test proves the guard still recognises what it looks for.
- **Statements in the new payment documents that did not match the code** were corrected after checking each against the code: how a repeated refund request is treated, what each "needs attention" flag means, the error for cancelling a paid order, the sort values, and "nine rules" that are ten.
- **Faults in the browser checks themselves**, none in the app: radio buttons that unmount when chosen, a result matched on a button as well as the message, an ambiguous order sentence, a UPI ID left by an earlier section, the deliberate 503 from a webhook with no secret set logged as unexpected, and one check label that described the cash limit as "an extra zero" when the rule is twenty times the bill plus 1,000 rupees (relabelled, and the browser run repeated).

**In 2.6.0:**

- **A recording with no speech could blank the open bill on the Order desk.** The reply to a silent recording carried no bill, so the screen showed an empty one while the server still held the customer's lines. Found by the voice-path tests. The server now returns the open bill with that reply and the screen leaves the bill alone (`test_release_260.py`, `OrderDesk.voice.test.tsx`).
- **A hung speech service could hold one request for up to 121.5 s** at the defaults: a call that had been sent and got no answer was tried three times and reported as a network error. Found by reading the client against the settings. It is now one call, limited to 20 s for speech to text and 15 s for text to speech, and reported as `TIMEOUT`. A connection that never opened, `429` and `5xx` are still retried. The 20 s figure is a calculated worst case; on a stand-in service that never answers a measured turn took 1,020 ms against 4,529 ms before, with the stated delays.
- **`.env` could be left half-written** if the process died while Settings rewrote it, and a Windows byte-order mark could hide the first key. It is now written to a temporary file and replaced in one step, other lines are kept as they were and a byte-order mark is read. The update never touches the file.
- **The new Voice diagnostics page scrolled sideways on a phone** (89 px too wide at 320, 49 at 360 and 19 at 390): two tables sat in their cards without the scroll wrapper and a long settings value would not wrap. No unit test saw it; the real-browser width sweep did. Fixed, and a unit test and the sweep now guard it.
- **A shop on its first day read ₹0 and 0 orders in the first three Analytics tiles** above charts showing that day's orders, because the tiles count complete periods only. Found by looking at the screenshots. Each tile now shows the unfinished period beside its total; totals and comparisons are unchanged.
- **Faults in the browser checks themselves, found before the final run.** The sidebar check ran before the sidebar had rendered, a deliberate 403 for the staff account was logged as an unexpected HTTP error, and the button audit hit the script's old time limit once and was rerun with a longer one. None was a fault in the app.
- **The realtime socket's deferred-audio mode was described in the docs but not tested.** Three tests were added (the turn first and the voice after, a failed voice still follows the turn, and the old shape without the option).

**In 2.5.0:**

- **A brand's pack-less alias belonged only to the pack imported first** ("amul butter" quietly became whichever Amul butter pack the shop had imported first). Found in the product-matching audit of the held-out brand results. Packs of the same brand now share the alias, so the parser sees several candidates and the dialogue asks which pack. Held-out result: wrong product 25 → 19, exact 252 → 244, asked which pack 2 → 16, not recognised 21 → 21. Existing shops keep the aliases they already have. Test: `test_branded_nlu.py`.
- **The new AI performance page scrolled sideways on a phone** (320 to 390 px; the browser run's width sweep failed with the page 447 px too wide at 320 px). Two causes: a filter row whose control refused to shrink below its content, and a long command in an empty-state message that could not wrap. Both fixed in the stylesheets, the front end rebuilt, and the whole browser run repeated on a fresh database: 148 of 148. No frontend unit test covers it (jsdom does not lay anything out); the browser check does.
- **Faults in my own browser checks, found and fixed before the final run.** The first check for the "no speech measured" notice failed because the page's badges are set in capitals by the stylesheet and `inner_text` returns the capitals; the "no claim of live verification" check matched the page's own wording "not live-verified" in the technology table; and a sign-in in the width sweep was answered with HTTP 429 once, because the script signs in many times in a short while. The script now compares in lower case, ignores "not ...", and waits a minute and tries once more when the dashboard does not appear (a second failure still fails the run). None of the three was a defect in the app.
- A first draft of two report charts had defects that were visible only on looking at them (a dual-axis chart, overlapping labels, a bar label cut off, a duplicated row); they were redrawn and every figure was looked at again.
- Order integrity, error leakage and the Windows scripts were reviewed line by line. **No oversell, duplicate-order or leakage defect was found**; tests were added so it stays that way (rows 11 and 16).

**In 2.4.0 (the redesign):**

- The first design-rule tests were written for the frontend runner, which does not load CSS, so they read an empty file and proved nothing. They were moved to `backend/tests/test_landing_design.py`, which reads the real stylesheet.
- The rule "no heading above weight 500" found four landing headings at 600; they were lowered. Looking at the signed-out screens then showed the sign-in title at weight 650 in the serif (too heavy) and the side tagline in bold sans; the title is now 500 and the tagline the serif at 400.

- The Marathi order-desk browser check failed once on a race: the disabled Confirm button exists before the parsed lines do. The check now waits for the two lines, then reports what it found.
- Re-running the browser script against a used database fails three checks (the setup checklist starts at 0 of 4 and the contact inbox is empty only once). That is how the script is documented (a fresh database); the passing run above used one.
