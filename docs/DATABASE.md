# Database

SWARA AI keeps everything in one database. The default is a **SQLite file** (`backend/data/swara.db`), opened through SQLAlchemy 2. No server
is needed. The tables below are generated from the models in `backend/app/models.py`; if you change a model, update this page (the schema is
also visible with `sqlite3 backend/data/swara.db ".schema"`).

## Conventions

| Topic | Rule |
|---|---|
| Money | **Integer paise** (`*_paise`). Never floats. 1 rupee = 100 paise. Totals are sums of line totals, rounded half-up per line |
| Quantities | `NUMERIC(12,3)`, handled as Python `Decimal` (kg, litres, pieces; 0.25 kg is exact) |
| Times | Stored as **UTC**, without a time zone marker. The interface and the CSV exports convert to IST |
| Primary keys | Integer ids, except `sessions.id` (a random string used by the voice/text conversation) |
| Foreign keys | Enforced (`PRAGMA foreign_keys=ON` on every SQLite connection). Journal mode is WAL, so readers do not block the writer |
| Secrets | Never stored in clear text: passwords are scrypt hashes, session and e-mail tokens are stored as SHA-256 hashes, the Gnani key is not in the database at all (it is in `.env`) |
| Demo data | Rows with `is_synthetic = 1` (orders, customers) were generated by `scripts/seed_db.py`. A **Demo data** switch in the app removes them from every view. Real orders taken on the Order desk are never synthetic |

## Tables

### Shop

| Table | What a row is | Notes |
|---|---|---|
| `products` | An item the shop sells: names in English, Gujarati and Hindi, unit, price, stock, reorder level, aliases the parser understands | `price_basis` says whether the price is a placeholder (`demo`) or one the shop set (`shop`). `source` is `curated` (the 65 staples that ship with the app) or `manual` (added by the shop, including items added from the public catalogue, which carry the catalogue `ean`). `sku` and `ean` are indexed. `cost_paise` is optional |
| `customers` | A person who orders: name, phone, preferred language, notes | `is_active` hides a customer without deleting their orders. The customer CSV export is owner-only |
| `orders` | One confirmed bill: status, channel (`voice` or `text`), language, customer, total | `status` is `confirmed`, `fulfilled` or `cancelled`. The order number shown to people (`SW-YYMMDD-n`) is computed from the date and id, it is not a column |
| `order_items` | One line of a bill | Copies the product name, unit and unit price **at the time of the order**, so a later price change never rewrites history. A product that has orders cannot be removed (foreign key) |
| `stock_movements` | Every change of stock: a negative `delta` for an order, positive for a cancel or restock | `reason` is `order`, `cancel` or `restock`; `order_id` links the movement to its order. Current stock lives in `products.stock`; this table is the audit trail |

### Conversations and speech

| Table | What a row is | Notes |
|---|---|---|
| `sessions` | One ordering conversation: the dialogue state (cart, language, what the assistant is waiting for) as JSON | Referenced by `turns` |
| `turns` | One message in a conversation (customer or assistant) with the measured time of each step (`stt_ms`, `nlu_ms`, `tts_ms`) | Feeds the **Conversations** screen. It stores the text of the conversation, **not audio** |
| `api_calls` | One call to Gnani: provider, model, ok/failed, status code, error type, latency, units | No text, no audio and no key. Feeds the latency figures on the **Conversations** screen and the hourly call budget |

### Public catalogue

| Table | What a row is | Notes |
|---|---|---|
| `catalog_items` | One packaged product from Open Food Facts (India): name, brand, pack size, category | About 5,325 rows, read-only in the app. `provenance` and `transforms` record what was cleaned; `name_raw` and `quantity_raw` keep the source values. `split` marks the rows held out for evaluation. **There are no prices in this table.** See [DATA.md](DATA.md) |

### Accounts

| Table | What a row is | Notes |
|---|---|---|
| `users` | A person who can sign in | `role` is `owner` or `staff`. `email` is unique. `password_hash` is scrypt. `preferences` is a small JSON object kept per user |
| `auth_sessions` | A signed-in browser | Only `token_hash` is stored; the cookie holds the secret. `csrf_token` is the per-session token the browser must send on writes. `expires_at` is the absolute end, `last_seen_at` drives the idle timeout, `revoked_at` is set on sign-out |
| `auth_tokens` | A single-use link for **e-mail verification** or **password reset** | `purpose` is `verify` or `reset`. Stored as a hash; `used_at` makes it single-use |
| `contact_messages` | A message sent through the landing-page contact form | `emailed` says whether a notice could be sent (it needs `SMTP_*`); `handled_at` is set by the owner |

### Payments (added in 2.7.0)

| Table | What a row is | Notes |
|---|---|---|
| `payments` | One attempt to pay an order | `method` (cash, upi, razorpay), `provider`, `status`, `amount_paise` (the order total when it was started), `amount_received_paise`, `refunded_paise`, `verified`/`verification`, provider ids (unique), `idempotency_key` (unique), `attention`, `created_by_id`/`confirmed_by_id`. Checks: amount above zero; refunded within 0 and the amount. A partial unique index allows **one `pending` payment per order** |
| `payment_events` | The audit trail of a payment | `source`, `event_type`, status before and after, `signature_ok`, `actor_id`, a one-line message, and a small JSON of whitelisted ids and amounts. `event_id` is unique, so a delivered Razorpay event is processed once. Never card data, secrets or signatures |
| `refunds` | A refund against a payment | `kind` (provider or manual), `amount_paise` (above zero), `status` (pending, processed, failed), `idempotency_key` (unique), `provider_refund_id` (unique) |
| `invoices` | One numbered invoice per order | `order_id` unique; `(year, seq)` unique; `number` like `INV-2026-000001`; the shop name as it was that day |
| `schema_migrations` | Which migrations have been applied | `2.7.0-payments` |

These tables are created by an additive, recorded migration (`backend/app/migrations.py`, run on start or with `scripts/migrate_db.py`) that first copies an existing database to `backend/data/backups/`. Foreign keys to `orders` and `users` do not cascade. Details: [MIGRATION_2.7.0.md](MIGRATION_2.7.0.md).

## Relationships

```
users 1 ──< auth_sessions            users 1 ──< auth_tokens
customers 1 ──< orders 1 ──< order_items >── 1 products
                      orders 1 ──< stock_movements >── 1 products
sessions 1 ──< turns                 customers 1 ──< sessions
```

## Creating, upgrading and resetting

- **Create / seed:** `setup.bat` runs `scripts/seed_db.py`, which creates the tables, the 65 staple products, the public catalogue (5,325 rows), and about 120 days of generated demo
  orders and customers (3,039 orders with the default `DEMO_HISTORY_DAYS=120`; the exact number depends on the day). Running it again changes nothing; `--reset` deletes local orders and stock changes first.
- **Upgrade in place:** on every start, `upgrade_schema()` in `backend/app/db.py` adds any column that a newer version needs to an older SQLite file
  (`ALTER TABLE … ADD COLUMN`), so no one has to delete their data. This is a small, explicit list (`ADDED_COLUMNS`), not a migration framework.
- **A database file created before the product was renamed** is still found and used if `swara.db` does not exist (`default_db_path()` in `config.py`), so an existing shop keeps its data.
- **Other databases:** any SQLAlchemy URL works through `DATABASE_URL` (for example PostgreSQL), but only SQLite has been run. For PostgreSQL you
  should adopt a real migration tool (Alembic) instead of `upgrade_schema()`, and review the JSON and numeric column types first.

## Integrity and concurrency

- **Confirming an order cannot oversell:** each line lowers stock with a conditional update (`UPDATE … WHERE stock >= qty`), so stock never goes
  negative even with two orders at once. If any line is short, the lines already taken are put back before anything is saved; the order, its lines and
  the stock movements are committed together. Cancelling returns the stock exactly once.
- **Input is parameterised** through SQLAlchemy; there is no string-built SQL for user input. A test stores SQL and script strings as data and
  reads them back unchanged.
- **Deleting:** the app deactivates products and customers (`is_active`) instead of deleting them, so history stays complete.
- SQLite allows one writer at a time. That is plenty for one shop's counter; it is the reason a busy multi-shop service would move to PostgreSQL.

## Backups

See *Data and backups* in [DEPLOYMENT.md](DEPLOYMENT.md): copy `swara.db` (and `-wal`/`-shm`) while the app is stopped, or use SQLite's
`.backup`. A backup contains customer names and phone numbers and order history, so protect it like the database itself. The `.env` file (Gnani key,
SMTP password) is **not** in the database and must be backed up separately and privately.
