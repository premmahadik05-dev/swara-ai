# Data: sources, provenance and limits

This page says where every piece of data in SWARA AI comes from, what was done to it, what it is licensed under, and what it cannot tell you. It replaces the earlier `DATASET.md`.

**The short version**

- The **product catalogue** (5,325 packaged products in India: barcode, brand, name, pack size, category) is **real, sourced data** from Open Food Facts. It has **no prices**.
- **Prices in this app are not real.** The 65 hand-written staples carry placeholder "demo" prices. A product you add from the catalogue gets the price *you* type, and is then marked as your own.
- **Orders and customers are generated** (labelled "Demo" everywhere in the UI) so the dashboard and analytics have something to show. Every analytic is computed from database rows; the *rows* are synthetic until you place real orders.
- Nothing here is a market price, a real sales figure, or a real person.

## Four kinds of data

Every row or file is exactly one of these, and the UI and the files say which.

| Class | Meaning | Examples here |
|---|---|---|
| **sourced** | Copied from a public source and not edited | Raw Open Food Facts file `data/raw/off_india_2026-07-05.csv`; the `*_raw` columns beside each cleaned value |
| **transformed** | Derived from sourced data by a deterministic, listed rule | Cleaned product name, parsed pack size, assigned shop category, train/test split |
| **curated** | Written by hand by the author | The 65 staples in `backend/app/seed_data.py` (names in three languages, spoken aliases, units, reorder levels) |
| **synthetic** | Generated by code or a template; imitates a pattern, records nothing | Demo orders and customers; demo prices; the test sentences |

Rows that mix classes keep them apart. In the catalogue, `name_raw` (sourced) sits next to `name` (transformed), and the Catalogue drawer shows both with a "sourced" / "transformed" tag and the cleaning steps applied.

## 1. Open Food Facts India (the real catalogue)

| | |
|---|---|
| **Source** | Open Food Facts, India database, https://in.openfoodfacts.org/ |
| **Licence** | Database: Open Database Licence (ODbL) 1.0. Contents: Database Contents Licence (DbCL) 1.0. https://opendatacommons.org/licenses/odbl/1-0/ |
| **Attribution** | Open Food Facts contributors, https://world.openfoodfacts.org/ (shown on the Catalogue page) |
| **How it was obtained** | From a volunteer's cleaned export of the OFF India database, GitHub `mvark/indiafoodstats`, pinned to commit `d3624c4e5b00d2e5aa6d9d3c4b0b24f82a7bbb5a`, file `data/all_2026-07-05.csv` |
| **Retrieved on** | 10 Nov 2026 (the snapshot itself is dated 5 Jul 2026 in its file name) |
| **File / integrity** | `data/raw/off_india_2026-07-05.csv`, 3,448,485 bytes, 21,751 rows, sha256 `dd54bd79…18370fe639` (full hash in `data/sources/MANIFEST.json`) |
| **Fields used** | `code` (barcode), `product_name`, `brands`, `categories`, `quantity`, `nova_group`, `nutriscore_grade`, `creator`, `last_modified_t` |
| **Result** | 5,325 products in the catalogue: 4,834 with a brand, 1,599 distinct brands, 12 shop categories |

**Why not straight from openfoodfacts.org?** The environment this was built in could not reach that host, nor `data.gov.in` or Kaggle. GitHub was reachable, so the republished export was used. One attempt to reach Open Food Facts through a browser was also blocked, and no other route was tried. On a machine with open internet, `python scripts/data/fetch_sources.py --update …` pins a newer snapshot (see the script's header) and `scripts/data/update_catalog.py` rebuilds and diffs the catalogue.

**Licence caveat, stated plainly.** The data is OFF's and is ODbL/DbCL. The *repository* it was retrieved through is licensed AGPL-3.0 (copy in `data/sources/indiafoodstats.LICENSE.txt`). Whether an AGPL repository can add conditions to a copy of ODbL data it did not create is not something this project can settle. If it matters for your use, fetch the data from Open Food Facts directly and re-run the pipeline. ODbL requires attribution and share-alike for a *derived database* that you publicly use, which is why the catalogue CSV carries its attribution and this file exists.

### What was done to it (`scripts/data/build_catalog.py`)

| Stage | Rows |
|---|---|
| Raw rows in the snapshot | 21,751 |
| After the filters below | 5,411 |
| After removing near-duplicates of a newer record | **5,325** |

Rows rejected, by the first rule that removed them (a row is counted once):

| Reason | Rows |
|---|---|
| Pack size blank or not parseable into kg / l / pieces | 10,596 |
| Blank product name | 3,119 |
| No kirana category found, or an excluded type (supplements, protein powders, pet food, infant formula, cosmetics, detergent) | 1,673 |
| Barcode not a valid EAN-13 (checked with the check digit) | 952 |
| Near-duplicate of a newer record | 86 |

Each kept row lists the rules applied to it in a `transforms` column: English name taken from the source's name list, HTML/spacing/capitalisation tidied, pack size read from the contributor's text and converted (g to kg, ml to l), shop category assigned from the source's category tags or the name, and a `train` / `test` split (4,798 / 527). **Nothing is invented**: a missing brand stays blank, no Gujarati or Hindi names are generated for these products, and there is no price column. `scripts/data/validate_catalog.py` fails the build if a price-like column appears, a required column is missing, a barcode is invalid or a provenance tag is not one of the four classes.

### Limitations of this source

- **Crowdsourced.** Names, brands and pack sizes can be wrong, out of date or typed inconsistently.
- **No prices, stock, sales or shop data of any kind.** It says what exists, not what a shop charges.
- **Skewed to packaged, branded food.** Loose staples (dal, rice, vegetables) are mostly absent, which is why the 65 curated staples exist.
- **More than half of the raw rows are unusable** (no pack size or name), so what remains is a biased sample of what contributors filled in completely, not of what sells.
- **Popularity is unknown.** The file has no scan counts. Rows are kept by completeness, not by how common they are on a shelf.
- **Categories are my mapping, not OFF's.** They are assigned from tag and name rules. A hand check of a sample during the build found roughly 89 to 90 percent of rows in a sensible shop category. The list of rows checked was not saved in the repository, so treat this as an indication, not a reproducible measurement.

## 2. Curated staples (65 products)

`backend/app/seed_data.py`: 65 everyday kirana items (vegetables, grains, pulses, spices, oil, dairy, snacks, household, and so on) with names in English, Gujarati and Hindi, units, reorder levels and spoken aliases in Latin, Devanagari and Gujarati script. These were **written by the author**. The **prices on them are placeholders** (`price_basis = demo`): plausible for a small town shop, not taken from any market survey. The Inventory page says so, shows a "Demo price" badge on each, and the Analytics page reports how many products still use demo prices. Editing a price and saving it changes the badge to "Shop price".

## 3. Synthetic orders and customers

| | |
|---|---|
| Where | `backend/app/seed.py`, seed 42; `scripts/seed_db.py` |
| What | Eight placeholder customers ("Demo Customer A" to "H"). By default about **120 days** of orders (set by `DEMO_HISTORY_DAYS`, clamped to 7 to 366): roughly 25 a day with busier weekends, 1 to 6 items each, popularity-weighted, shop hours 07:00 to 21:59 IST with morning and evening peaks, about 4% cancelled |
| Mixes (random draws) | Language: 40% Gujarati, 25% Hinglish, 20% English, 15% Hindi. Channel: 60% "voice", 40% "text" |
| Flag | Every generated row has `is_synthetic = true`. The UI labels it "Demo". The global **Demo data** switch (top bar) includes or hides it everywhere |

Because the history is generated, the "voice share" and the busy hours on a fresh install describe the generator, **not** a shop. Orders you take on the Order desk are saved as real (`is_synthetic = false`) and are counted as real. Turn Demo data off to see only your own.

The charts are honest computations over whatever rows exist; the Analytics page repeats the demo-data warning whenever synthetic rows are included. A week-over-week or month-over-month change is shown **only** when the earlier window is complete and at least half of its periods contain orders. Otherwise the page says "Not enough earlier data to compare" instead of printing a percentage that would be arithmetic, not a trend.

To regenerate: `backend\.venv\Scripts\python.exe scripts\seed_db.py --reset` (deletes local data).

## 4. Test data (kept separate)

| File | Class | What it is | Used by |
|---|---|---|---|
| `eval/utterances.jsonl` | synthetic + authored | 288 order sentences for the 65 staples: 128 written by the author (Gujarati, Hindi, Hinglish, English) and 160 generated from templates | `scripts/evaluate_nlu.py`, `backend/tests` |
| `data/test/branded_utterances.jsonl` | synthetic sentences, sourced product identities | 300 templated sentences ("bhaiya 2 {name} chahiye", and so on in four languages) for products from the **held-out `test` split** of the catalogue | `scripts/evaluate_branded.py` |
| `data/test/branded_results.json` | measured | Output of the last branded evaluation | EVALUATION.md |

The held-out split (527 products, a random 10%) is never used to write or tune alias rules, so the branded evaluation is not judged on products the matcher was tuned on. It is still **optimistic**: it is a random split of the same crowdsourced catalogue (so brands and naming patterns are shared with the training part), the sentences are built from the product's own name, and it is text only (no speech recognition). Results are in [EVALUATION.md](EVALUATION.md).

## 5. Audio

No recordings are included. The Noise lab records **your** voice in your browser (kept in memory, never stored). `scripts/verify_gnani.py` and `scripts/evaluate_noise.py` use audio synthesised by Gnani Timbre from the short phrases in `scripts/_live.py`; synthesised speech is cleaner than a human voice, so those results are a smoke test.

## Sources considered and not used

| Source | Why not in this build | How you could add it |
|---|---|---|
| Open Prices (prices.openfoodfacts.org) | Host blocked by the build environment (one attempt through a browser was blocked too; no workaround was tried) | Download the CSV on a machine with internet, place it in `data/raw/`, and extend `build_catalog.py` to join on barcode. Crowdsourced prices vary by shop and city and would still need a "last seen" date |
| Department of Consumer Affairs retail prices (data.gov.in) | Host unreachable from the build environment; bulk access also needs an API key | Same route. These are commodity-level prices (rice, atta, dal) and would feed a *reference price*, never a branded product's price |

Because neither was available, **no real price data exists in this project**, and none is claimed.

## Reproducing the data

```bat
python scripts\data\fetch_sources.py          :: verify the committed raw file against the pinned hash
python scripts\data\update_catalog.py         :: verify, rebuild the catalogue, validate, print what changed
python scripts\data\make_test_set.py          :: rebuild the held-out branded test sentences
python scripts\evaluate_branded.py            :: measure product-name recognition on them
python scripts\seed_db.py --reset             :: regenerate the demo shop (deletes local data)
```

`GET /api/catalog/source` returns the same provenance (source, licence, retrieval date, limitations) the Catalogue page shows.
