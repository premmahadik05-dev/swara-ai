# Payment module: security audit (2.7.0)

**Who wrote this and what it is.** It is a self-audit by the author of the payment module: the code was read against a checklist, and each control below is tied to a test that exercises it.
It is **not** an independent review, a penetration test or a PCI DSS assessment, and **nothing here was tested against the real Razorpay service** (see "Not verified"). Treat it as an honest list of what was built and checked, and of what is left for you to check.

## Scope

The payment module: `backend/app/services/payments.py`, `services/razorpay.py`, `routers/payments.py`, the payment parts of `routers/orders.py`, `routers/settings.py`, `security.py`, `config.py`, `migrations.py`, the models, and the front-end payment screens and API client.
The voice-ordering path, the language engine and the Gnani integration were not changed by this module and are outside this audit (they were covered by the 2.6.0 checks).

## Your ten security rules, one by one

| # | Rule | How it is met | Proof (test names; all in `backend/tests/` unless marked FE = `frontend/src`) |
|---|---|---|---|
| 1 | Never expose the Razorpay key secret in front-end code | The secret is a `SecretStr` read from `.env` by the server only. The browser receives the public key id and the provider order id, nothing else. No payment response contains a secret, and Settings shows only "Set" or "Not set" | `test_no_razorpay_credential_or_secret_name_appears_in_frontend_source` (scans the front-end source and the built bundle; it allows exactly two field names, `key_secret_set` and `webhook_secret_set`, which are yes/no answers from the server, and the made-up `rzp_test_PLACEHOLDER01` in tests; `test_the_frontend_guard_recognises_what_it_looks_for` checks the guard fires), `test_no_secret_appears_in_any_payment_response`, `test_secrets_are_hidden_when_settings_are_printed` (`test_payments_security.py`, `test_payments_razorpay.py`); FE `PaymentsSettingsCard.test.tsx` (each secret is shown only as set or not set, never a value); browser run: the Payments card has no password input; browser run: the config the page receives has no key or secret |
| 2 | Never hardcode payment credentials | There are none in the code. `.env.example` has the four names, empty. The only key-shaped strings in the tree are made-up placeholders used by tests (`rzp_test_PLACEHOLDER01` and similar) | `test_no_credential_is_hardcoded_anywhere_in_the_backend`, `test_env_example_has_only_empty_placeholders_for_payments_and_keeps_the_gnani_lines`; tree scan (below) |
| 3 | Never request real credentials in chat | No real Razorpay credential was requested, received or used while building this. Tests use a stand-in for Razorpay and made-up placeholder values. This guide and the setup guide tell you to keep keys in `.env` only | Process rule; see also `docs/RAZORPAY_SETUP.md` |
| 4 | Secrets in backend environment variables | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `PAYMENT_MODE` are read from the environment or `.env` at start. Settings in the app can set the shop's UPI ID but **cannot** write payment secrets | `test_the_default_configuration_has_razorpay_off_in_test_mode`, `test_secrets_never_appear_in_logs_even_when_razorpay_refuses_the_key` |
| 5 | Verify webhook signatures | HMAC-SHA256 over the **raw bytes** with the webhook secret, constant-time comparison (`hmac.compare_digest`), checked before the body is parsed. No webhook secret means every webhook is refused (503). Missing or wrong signature is 400 and records nothing as paid | `test_a_webhook_with_a_bad_or_missing_signature_is_refused_and_changes_nothing`, `test_webhooks_are_refused_when_no_webhook_secret_is_set`, `test_signature_functions_follow_razorpays_documented_construction_and_reject_junk`, `test_a_signed_captured_event_marks_the_payment_paid_without_any_signed_in_user`; browser run: an unsigned webhook is refused |
| 6 | Never trust the front end's payment success | The screen never marks anything paid. The server verifies the checkout signature **and then asks Razorpay** for the payment. The order id that is checked is the one the server stored, not the one the browser sends. The dialog shows "Payment received" only from the server's reply | `test_a_browser_claim_of_success_cannot_mark_anything_paid`, `test_a_wrong_signature_is_refused_and_nothing_is_marked_paid`, `test_the_signature_must_be_for_the_stored_order_not_the_one_the_browser_names`, `test_a_genuinely_signed_payment_that_razorpay_does_not_know_is_not_marked_paid`, `test_when_razorpay_cannot_be_asked_a_valid_signature_alone_does_not_mark_paid`; FE `PaymentDialog.test.tsx` (status only from the server's reply, including after a decline or a closed window) |
| 7 | Validate the amount against the server-side order total | The browser never sends an amount for a payment. The Razorpay order is created for the order's total held by the server, and the reply's amount is checked. Every confirmation (checkout, check status, webhook, QR) compares amount, currency and order before marking paid; a mismatch sets `amount_mismatch` and the payment stays unpaid | `test_the_amount_due_is_the_server_side_order_total_whatever_the_browser_sends`, `test_every_amount_checked_comes_from_the_server_side_order_total`, `test_a_provider_order_with_the_wrong_amount_is_refused_and_nothing_is_started`, `test_a_valid_signature_for_a_payment_razorpay_says_is_for_a_different_amount_is_not_marked_paid`, `test_a_webhook_amount_that_differs_from_the_bill_is_not_marked_paid`, `test_a_qr_payment_of_the_wrong_amount_is_not_marked_paid`; FE `api.startPayment` sends only the way and a key |
| 8 | Prevent replay attacks and duplicate processing | Each webhook event id is stored under a uniqueness rule, so a redelivery is acknowledged and ignored. A signature for one payment cannot confirm another. Provider ids are unique in the database. One open payment per order is a database rule. Requests carry idempotency keys. Refunds are idempotent; refunded plus waiting money is capped at the amount paid by the code, and refunded money is also capped by a database check | `test_the_same_webhook_delivered_twice_is_processed_once`, `test_a_redelivery_with_a_new_event_id_after_payment_changes_nothing`, `test_a_webhook_without_an_event_id_header_is_still_deduplicated_by_its_content`, `test_an_old_failure_replayed_after_success_does_not_undo_it`, `test_a_signature_for_one_payment_cannot_be_replayed_to_mark_another_paid`, `test_a_captured_event_replayed_against_a_different_order_is_ignored`, `test_the_database_itself_allows_only_one_open_payment_per_order`, `test_the_database_refuses_nonsense_amounts_and_duplicate_provider_ids`, `test_the_same_idempotency_key_returns_the_same_payment`, `test_the_same_refund_request_twice_makes_one_refund`, `test_refund_rows_cannot_exceed_the_payment_in_the_database`, `test_a_second_captured_payment_for_a_paid_order_is_flagged_not_recorded_twice` |
| 9 | Enforce owner and staff permissions | Server-side dependencies: refunds, payment analytics, refund refresh and the UPI settings are **owner only**; everything else needs a signed-in account; writes need the CSRF token; nothing works signed out except the signed webhook. The screens hide what a role cannot do, but the server is what refuses | `test_staff_can_take_payments_but_not_refund_or_see_analytics_or_change_settings`, `test_staff_cannot_refund_and_a_failed_attempt_changes_nothing`, `test_nothing_in_the_payment_api_works_without_signing_in`, `test_writes_need_the_csrf_token`, `test_the_webhook_is_the_only_payment_route_without_a_session_and_it_needs_the_signature`, `test_a_payment_request_from_another_website_is_refused`; browser run: staff get 403 from the analytics and refund routes and see no refund form |
| 10 | Log payment events without sensitive card or UPI PIN data | The app never has a field for a card or a PIN: Razorpay Checkout collects those in Razorpay's own window. The audit trail keeps only whitelisted scalar fields (ids, amounts, statuses, a reference); everything else in a webhook, such as e-mail, phone, UPI IDs and card fragments, is dropped before storing. Signatures and secrets are not stored or logged | `test_the_audit_trail_stores_ids_and_amounts_but_never_a_signature_or_secret`, `test_personal_data_in_a_webhook_is_not_stored`, `test_secrets_never_appear_in_logs_even_when_razorpay_refuses_the_key` |

## Other controls

| Control | Where | Proof |
|---|---|---|
| **Live payments never turn on by themselves.** Razorpay is off until keys are set; test keys need `PAYMENT_MODE=test`, live keys need `PAYMENT_MODE=live` and a `rzp_live_` key id; a mismatch is refused with the reason | `config.py` | `test_live_mode_never_turns_on_by_itself`, `test_live_mode_works_only_with_live_keys_and_is_never_implied_by_test_keys`, `test_razorpay_stays_off_for_bad_or_mismatched_keys` |
| **Browser policy follows the setting.** The content-security policy, permissions policy and window-opener policy allow Razorpay's domains only while Razorpay is switched on; with it off the headers are as in 2.6.0. Payment responses are `no-store` | `security.py` | `test_content_security_policy_allows_razorpay_only_when_razorpay_is_on`, `test_response_headers_follow_whether_razorpay_is_on`, `test_payment_responses_are_not_cached`; browser run: no `razorpay` in the policy when Razorpay is off |
| **A person's word is never "verified".** A UPI QR for the shop's own UPI ID cannot see the money. It stays `verified: false` / `verification: "manual"` and is labelled "Not verified" on screen, on the invoice and in analytics until, and even after, a person confirms it with a reference. Cash is `verification: "cash"` | `payments.py`, front end | `test_manual_upi_is_never_paid_until_a_person_confirms_it_with_a_reference`, `test_manual_upi_collections_are_reported_separately_as_unverified`; FE `UpiQr.test.tsx`, `PaymentDialog.test.tsx` (the confirm button stays off until the checkbox and a reference are both given) |
| **Money held blocks cancelling the order.** An order with collected, unrefunded money cannot be cancelled (409 `PAID_ORDER`); the owner refunds first | `routers/orders.py` | `test_a_paid_order_cannot_be_cancelled_until_it_is_refunded`, `test_a_partly_refunded_order_is_still_blocked_from_cancelling` |
| **Payments never touch stock**, so a retry, a duplicate webhook or a refund cannot deduct inventory twice | design | `test_payment_attempts_and_retries_never_change_stock` |
| **Refunds are never assumed.** A Razorpay refund stays "Waiting" until Razorpay reports it processed; a later "failed" or "pending" report cannot undo a processed refund; a reply with a different amount is not applied | `payments.py` | `test_a_razorpay_refund_is_pending_until_razorpay_confirms_and_the_payment_stays_paid`, `test_a_late_failed_or_pending_report_cannot_undo_a_processed_refund`, `test_a_razorpay_reply_with_a_different_refund_amount_is_not_applied`, `test_when_razorpay_does_not_answer_the_refund_is_not_assumed_done_and_can_be_found_by_receipt` |
| **Webhook input is bounded.** 256 KiB limit; non-JSON refused; events this shop does not know are acknowledged and ignored | `routers/payments.py` | `test_webhook_bodies_that_are_not_json_or_are_too_large_are_refused`, `test_a_webhook_for_something_this_shop_does_not_know_is_acknowledged_and_ignored` |
| **Existing data is protected by the migration.** Only new tables are created, after a consistent backup; row counts of users, orders, products, customers and stock are compared before and after | `migrations.py` | `test_nothing_in_the_migration_can_delete_or_change_existing_data`, `test_migrating_an_older_database_backs_it_up_adds_the_tables_and_changes_nothing_else`, `test_the_payment_tables_point_at_orders_without_cascading_deletes` |
| **Gnani settings are untouched** | design | `test_the_gnani_settings_are_untouched_by_the_payment_module` |

## Not verified, and residual risks

Read these before you rely on the module.

| Item | Status |
|---|---|
| **Real Razorpay behaviour** | **Not verified.** Every Razorpay call was tested against a stand-in (an HTTP mock returning the replies the code expects). The endpoints, field names, signature construction and event names were written from Razorpay's public documentation as remembered while building, not from a live call. A difference would show up in your first test-mode payment (checklist in `RAZORPAY_SETUP.md`) |
| **Razorpay Checkout in a real browser** | **Not verified.** The script is loaded on demand from Razorpay's address (`https://checkout.razorpay.com/v1/checkout.js`, written from memory); the build environment cannot reach it. The browser tests stop before opening it and test the screens' reaction to a decline, a closed window and a failed script load with a stand-in |
| **Razorpay's UPI QR (`RAZORPAY_UPI_QR`)** | **Not verified**, and needs Razorpay to enable it for the account. Off by default |
| **Live mode** | Never run. No claim is made about live payments |
| **Webhook endpoint is not rate limited.** It is unauthenticated by design; each call costs one HMAC over at most 256 KiB, after which an invalid call is dropped. A hostile caller can make the server do that work. If the app is exposed to the internet, put a reverse proxy rate limit in front of `/api/payments/webhooks/razorpay`. (The other payment routes share the app's per-address limit.) | Residual risk |
| **Trust in people.** Staff can record cash and confirm a UPI QR. These are not provider-verified. Each is recorded with who and when, shown separately ("confirmed by hand"), and counted apart in analytics; but the app cannot tell a true confirmation from a false one | By design; the owner reviews |
| **Data at rest.** The SQLite database and its backups hold payment records (ids, amounts, references, the shop's UPI ID) unencrypted, like the rest of the shop's data. No card data and no secrets are in them. Protect the computer and the backups | Residual risk |
| **Single-process deployment.** Duplicate protection leans on database uniqueness, which also holds with several workers on one SQLite file, but the app is built and tested for the one-process setup described in `SECURITY.md` | As in 2.6.0 |
| **Tax.** No GST details are configured, no tax is calculated, and the invoice says it is not a GST tax invoice. No compliance claim is made | By design |
| **PCI DSS** | Not assessed. By design the app never receives card data (Razorpay's window collects it), which is a reason to expect a small scope, not a statement of compliance |
| **Windows scripts and the Windows installer path** | Not run here (the build environment is Linux) |

## Findings while building and testing

Things found by running the code, not by reading it, and fixed before release:

- **Screen allowed a cash amount the server refuses.** The server rejects a cash amount over 20 times the bill plus ₹1,000 as an obvious slip (for example a stray run of extra digits). The cash window did not know that and enabled its button, then failed. Found by the browser test; the window now applies the same rule before sending, and a test pins it.
- **Reopening a payment flashed the wrong screen.** The window showed "choose a way to pay" for one network round trip before resuming a payment already in progress. Found by the browser test; the window now waits for everything it needs and a test fails on the old behaviour.
- **Wording that overstated.** A cash payment was labelled "Unverified" and the invoice repeated "not verified by a payment provider" twice. Both fixed; "Unverified" now appears only for a UPI QR confirmed by hand.
