# Limitations

Stated plainly, so nobody has to find them out.

## About payments (2.7.0)

- **A UPI QR for the shop's own UPI ID cannot see the money.** It is labelled "Not verified" everywhere until a person confirms it, and even then it stays "confirmed by hand" rather than "verified". Only Razorpay can confirm a payment by itself, and only once it has been set up and tested by you.
- **Cash and hand-confirmed UPI rely on the person recording them.** The app records who and when and counts them apart in analytics, but cannot check them.
- **The invoice is not a GST tax invoice.** No merchant tax details are configured and no tax is calculated; the invoice has no discount lines (the field is zero). Do not use it where a tax invoice is required.
- **No customer UPI IDs, card numbers or PINs are ever stored**, so a payment shows only what the shop typed (a bank reference) or what Razorpay's ids say.
- **Razorpay sessions and real-money behaviour are unknown here**: timeouts, retries by Razorpay, how late a webhook can arrive, and the exact fields on a live payment. The code treats a payment as unpaid until it can prove otherwise, so a surprise should look like "Waiting", not "Paid".
- **Refunds to a customer's account take the time Razorpay takes**; the app shows "Waiting" until Razorpay says processed. Cash refunds are the owner's own act; the app records that it was done.
- Not supported: part-payments across ways (one payment per order at a time; a second can start after the first fails or is cancelled), tips, split bills, discounts, payment links sent to a customer, subscriptions, and settlement reports.

## About the 2.4.0 redesign

- **Typography is judged by eye and by rules, not by a reader study.** The type system was reviewed on screenshots at 1440, 768 and 390 px (and 320 px in the overflow check), and the stylesheet rules
  are tested (`backend/tests/test_landing_design.py`). Nobody outside the project has read the page; no usability test, no Lighthouse or axe run and no screen-reader pass was done.
- **Newsreader has no Indian-script glyphs.** A heading in Gujarati or Devanagari falls back to the Noto Sans face for that script (the font stack lists them), so those headings are a sans, not
  a serif. The landing page's headings are English; Indian-script text appears in sample sentences, names and rows, all in Noto Sans.
- **The footer's "API reference" link goes to the backend's own `/docs` page.** It exists unless the owner sets `API_DOCS=false`; with that setting the link shows a 404. The landing page is
  served by the same backend, so in the usual setup the two are always together; behind a separate static host the link would be dead.
- **No GitHub link.** The brief asked for one where a valid destination exists; this project has no public repository address on file, so none is shown. The footer has no social links for the same reason.
- **The screenshots on the landing page are of demo data**, and say so under each picture. They are regenerated with `scripts/take_screenshots.py --landing`; if the app's look changes they go stale until that is re-run.
- **The product areas make claims about the code, not about outcomes.** There are no customer numbers, speed figures or accuracy claims on the page, because none have been measured with real shops.
- **The page was checked in Chromium only** (headless, desktop, tablet and phone sizes); Safari and Firefox were not run.

## About the 2.5.0 evaluation, stock ledger and report

- **No live Gnani evidence exists for any number in the AI performance page or the report.** Speech recognition accuracy, word error rate, speech and end-to-end latency and acoustic-noise behaviour show "Not measured" and are not estimated. The response times shown are local HTTP on one Linux machine with no Gnani call.
- **The stock ledger starts when 2.5.0 does.** Seeded demo orders write no ledger rows, and the opening stock of a product imported from the catalogue is not in the ledger, so "opening" is derived (current stock minus net movements) and a fresh database shows an empty movement table until real orders, restocks, cancellations or adjustments happen.
- **The demo tables in the report come from a scripted session** (`scripts/demo_activity.py`: six typed orders, two restocks, one cancellation, four imported products at prices typed for the demo; with `--payments`, also four payments, one part refund and one invoice, none through Razorpay) on top of generated demo orders. They show the screens, not a shop's results.
- **Report and figures are built on one machine.** `scripts/build_report.py` needs `matplotlib`, `pandoc` and Playwright's Chromium, none of which the app needs; the Word copy is pandoc's plain conversion and has not been opened in Microsoft Word.
- **A fix made existing shops' behaviour differ from new shops'.** The pack-family alias fix applies to products imported on 2.5.0; a shop that already imported a product family keeps the aliases it has until the products are re-imported.

## About the numbers

- Language results are on **sentences I wrote**, scored on **transcripts, not audio**. The 288-utterance evaluation and the 300 branded-product sentences cover the original four languages only. Since 2.5.0 the seven added languages also have a small authored sentence set (70 sentences in all eleven languages, 648 for the language-label check); the figures for those seven show only that the parser agrees with its author, because **no native speaker has reviewed the sentences**, and with 7 to 9 sentences per language one miss moves a percentage a lot. The same person wrote the parser and the test set, and fixes were tuned on that set. See [EVALUATION.md](EVALUATION.md).
- Speech accuracy, speech latency, streaming latency, acoustic-noise robustness and `bias_list` benefit are **unmeasured**, for all eleven languages.
- Simulated transcript noise (random character damage) is a proxy; it is not acoustic noise and not Prisma's real error pattern.
- Latency was measured on one Linux machine over loopback; it excludes Gnani.
- Analytics on a fresh install are computed over **synthetic** orders (about 120 days, roughly 3,000 orders, drawn by a seeded generator). Every figure is an exact sum over the rows in the database, but the rows are made up: the totals, best sellers, busy hours and the "voice share" say nothing about any real shop. The Demo data switch and the labels on each page say so, and the switch removes them from every view.
- The category of an imported catalogue item comes from keyword rules on Open Food Facts' own category tags. I checked a sample by hand and judged it roughly 89 to 90% right; that sample list was not saved, so the figure cannot be reproduced and should be read as an impression, not a measurement.
- Short romanised spellings of staple names in the seven added languages are not matched by sound alone (see [LANGUAGES.md](LANGUAGES.md)); this was a deliberate trade against short brand words being read as staples.
- The held-out branded-product result (244 of 300 exact = 81.3%, 19 wrong product = 6.3%, 16 asked which pack, 21 not recognised; 2.3.0 and 2.4.0 reported 252 / 25 / 2 / 21 before a pack-family alias fix) is on **templated text** that is built from the product name and never states a pack size. By the author's reading of the list (not part of the stored results), about half of the 19 wrong products are a generic or larger pack of the same item rather than a different item; all 19 are scored as wrong. See [EVALUATION.md](EVALUATION.md).
- **Noise is character damage, not sound**, and the 5-seed spread shown on the AI performance page is the spread over random damage patterns, not a confidence interval of accuracy on real speech.
- **The test record is only as old as its logs.** The AI performance page and the report build their "Test and verification record" from the saved logs in `docs/test-results/`; a row says "Not run" when its log does not exist, and shows the log's date. After changing the code, re-run the suites and `python scripts/build_verification_summary.py`.
- "Change vs the earlier period" is shown only when the earlier window is complete and at least half of its periods had orders; otherwise the page says there is not enough earlier data. That is a rule I chose to avoid misleading percentages, not a statistical test.

## About the product

- **Evon v3.3 is not used** (not on Gnani's public API). Reasoning is a deterministic engine, which is safe but cannot handle phrasing the grammar and lexicon do not cover. There is no model-based fallback in this repository; an adapter is described in [EVON.md](EVON.md) as future work and is untested.
- **Catalogue-bound.** The assistant understands the 65 curated staples, their aliases, and whatever you import from the Open Food Facts catalogue (brand and name only, no hand-written aliases). Unknown items are reported as "not in this shop", never invented. A new product is immediately orderable with the aliases you type, but spelling variants you did not list rely on phonetic and fuzzy matching.
- **Weak matches become questions.** The matcher is sensitive to spelling damage (see the simulated-noise table). In production this shows up as more follow-up questions, which is the intended failure mode, but it will annoy customers if Prisma's output is poor.
- **Language scope.** Eleven choices: Gujarati, Hindi, English, Hinglish (in use since the first release) and Marathi, Bengali, Tamil, Telugu, Kannada, Malayalam, Punjabi (added in 2.3.0): the ten languages Gnani documents for Prisma v2.5 and Timbre v2.5, plus Hinglish. Other languages are not handled. Prisma v2.5 takes one language per request, so a sentence that switches language mid-way depends on how Prisma transcribes it; Prisma v3.0 (auto language, code-mix) is available as a setting and is untested here. **Auto-detect and mixed-language are refused on v2.5** with a clear error; before 2.3.0 they were silently treated as Gujarati. See [LANGUAGES.md](LANGUAGES.md).
- **The seven newer languages are authored, not native-reviewed.** Their number words, unit words, filler words, product names and reply templates were written by the project author for this release and are covered by unit tests the same author wrote. No native speaker has reviewed them, they have **not** been compared with real Prisma output, and they will miss colloquial and regional forms. Several scripts are matched to products through a Devanagari phonetic spelling plus stripping of case endings, so words that sound alike can be confused (the engine asks when two products fit, and never guesses stock). Their product names exist only for the 65 curated staples; imported catalogue products have English names.
- **Hindi and Marathi share a script.** Marker words decide; otherwise the language chosen in the selector does; with neither, a sentence made only of shared words is read as Hindi.
- **A switched-off language is not offered for voice, but typing is not blocked.** `DISABLED_LANGUAGES` (or the switch in Settings) removes a language from the selector and makes the voice and typed-turn APIs refuse it when it is named. A sentence typed in that language **without** naming it is still understood, because the engine works the language out from the characters. English cannot be switched off.
- **Automatic number formatting** (`transcribe`) is documented by Gnani only for Hindi and English, so the other languages rely on this project's own number-word rules. Gnani says text normalisation for speech is deepest for Hindi, Marathi, Tamil and English; spoken numbers and units in the other six may sound less natural.
- **Gnani's realtime documentation is inconsistent about the language header** (`lang_code` in one place, `language_code` in another). The app sends both; which one Gnani honours has not been tested.
- **The live status of a language comes from a file** (`eval/results/live_verification.json`) written by `scripts/verify_gnani.py` on your machine. Three of its four checks are weak by design: `stt_code` sends a generated tone and proves only that the code is accepted; `stt_loopback` feeds Timbre's synthetic voice to Prisma; only `stt_human` (a recording of a person you supply) says anything about real recognition, and one speaker saying one sentence is a very small sample.
- **No real prices exist in this project.** The public catalogue (Open Food Facts India, 5,325 products) has names, brands, quantities, categories and barcodes but **no prices**. The 65 curated staples carry demo prices, shown with a "Demo price" badge. An imported item is only added once the shopkeeper types the price, and is then shown as the shop's own price. Inventory value is at selling price, because no cost price is recorded.
- **Stock and order history of imported items are the shop's own.** Importing a product creates it with the stock you enter; nothing about quantities or sales comes from the public data.
- **No pricing rules.** One price per product: no discounts, GST, weights-and-measures rounding rules, or credit (udhaar) accounts.
- **Demand insights are simple.** "Days of cover" is stock divided by the recent daily sales rate, and the suggested reorder tops stock up to 14 days of cover. It is arithmetic on the shop's own orders, not a forecast; it ignores weekdays, festivals and price changes.
- **Single shop, single till.** One database is one store with one set of stock. There are accounts (owner and staff, see below), but no separate shops, branches, organisations or per-person permissions beyond those two roles.
- **No payments, no delivery, no tax invoice.** A bill can be printed from the Orders screen through the browser's print window (or saved as PDF from there): a plain receipt layout with the shop's name, the lines and the total. There is no thermal-printer (ESC/POS) driver, no GST breakdown and no bill numbering other than the order code.
- **Exports are CSV only.** Orders, stock and customers can be downloaded (orders and stock by anyone signed in, customers by the owner only). Each file is capped at 20,000 rows (the response says so when it cuts), there is no XLSX or PDF export, no scheduled or e-mailed report, and nothing can be imported back from them. Once a file is downloaded it is outside the app's control; the customer file holds phone numbers.
- **Low-stock alerts are in the app only.** They appear on the Dashboard, the Inventory filters and right after an order that takes an item below its reorder level. Nothing is pushed: no notification bell, e-mail, SMS or WhatsApp message.
- **Barge-in** (customer interrupting the assistant) is handled by muting the microphone while a reply plays, not by true full-duplex.
- **Synthetic noise.** The Noise lab's crowd noise is generated speech-shaped babble, not a recording.
- **Replies are templated.** Quantities in replies are written as numbers: a Hinglish reply says "0.5 litre" where a person would say "aadha litre". Timbre speaks what the reply text says.

## About accounts, the landing page and deployment

- **The shop's name is kept in `.env`** (as `STORE_NAME`) when the owner changes it in Settings, so it needs a writable `.env` and, like the Gnani key, is shared by nothing but that one process. The dashboard's setup checklist remembers "Hide" in the browser's local storage, per person and per browser; it is a first-run aid, not a record.

- **Sign-in is local accounts only.** There is **no Google, Microsoft or other OAuth sign-in**, no single sign-on, no two-factor sign-in and no passkeys. Adding OAuth needs credentials and a registered redirect address from the provider and new backend routes; see [AUTHENTICATION.md](AUTHENTICATION.md).
- **E-mail is optional and was not tested against a real provider.** Without `SMTP_*` settings nothing is e-mailed: password reset links and verification are unavailable (the owner resets passwords from the command line) and contact-form messages are only saved. With SMTP the message building and the flows were tested against a small local SMTP server; the STARTTLS, SSL and SMTP-login paths and any real provider were not. `auth_admin.py test-mail` checks yours.
- **People management is thin.** The owner can turn accounts on and off. There is no screen to invite or add a person (use `auth_admin.py create-staff`), no way to change an e-mail address, change a role, or delete an account, and no account-data export or erase request flow (shop records can be exported as CSV, see above). One owner only.
- **Open sign-up and first-owner defaults suit a laptop, not the internet.** See [SECURITY.md](SECURITY.md) (known risks 1 to 3). `OWNER_EMAIL`, `ALLOW_SIGNUP=false` and `PUBLIC_DEMO=false` are the settings to change for a real shop.
- **Terms of Service and Privacy Policy are templates** written for this project, in plain language, and say so on the page. They are not legal advice and have not been reviewed by a lawyer. Replace them before using the app with real customers or staff.
- **The landing page contains no customer stories, partner names, customer counts or performance claims**, because there are none to report. Its pictures are real screenshots of this app running on **generated demo data**, labelled that way on the page. Its Technology section separates what is built from what is planned.
- **The landing page's live demo uses the language engine on typed text.** Voice needs a Gnani key and a signed-in session.
- **Search and sharing tags that need an absolute address** (canonical, `og:image`) appear only when `PUBLIC_URL` is set when the front end is built. There is no `sitemap.xml`.
- **Not measured:** page speed (no Lighthouse or WebPageTest run), real-user performance, behaviour behind a real reverse proxy or on https with a certificate, Safari and Firefox, screen readers, password managers.

## About the engineering

- **Single process.** The rate limiters, the sign-in lock-out counters and the Gnani call budget live in process memory, and the TTS cache is a local folder. Running several workers needs shared state (for example Redis) for those, and PostgreSQL instead of SQLite. [DEPLOYMENT.md](DEPLOYMENT.md) explains what goes wrong otherwise. **Pressing Confirm twice makes one order only because the confirm handler runs on one event loop in one process**; there is no row lock or version column on the session record, so with several workers two near-simultaneous presses could in principle each save the bill (stock still never goes negative). Tests cover double presses and two buyers of one unit ([SECURITY.md](SECURITY.md)).
- **SQLite by default.** The code is plain SQLAlchemy 2 and intended to be PostgreSQL-ready, but it has **only been run on SQLite**. The atomic stock update (`UPDATE … WHERE stock >= :qty`) is portable; other SQLite-specific behaviour has not been audited for PostgreSQL.
- **No migrations tool.** Tables are created with `create_all`, and `upgrade_schema` adds missing columns on SQLite so an older v1.0 database keeps its data (covered by a test). That is not a general migration system; real use on PostgreSQL needs Alembic.
- **No audit log** beyond stock movements, the API-call log and the server log lines for sign-in events. Nothing records who changed a price or cancelled an order.
- **Analytics aggregate in Python** over the window; fine for thousands of orders (the benchmark in [EVALUATION.md](EVALUATION.md) used about 3,100), not for millions.
- **Changing the demo history length needs a reset.** `DEMO_HISTORY_DAYS` only applies when the database is first seeded; to regenerate, run `seed_db.py --reset`, which deletes local data.
- **Frontend runs on a static build.** The ZIP contains a prebuilt `frontend/dist`. Editing the frontend source needs Node 20.19+ (or 22.12+) and `npm run build`; the development server is not what `start.bat` runs.
- **The key is stored in `.env` in plain text** (that is how Gnani issues it and how most local tools work), as is the SMTP password. Anyone who can read your disk can read them. Only the owner can set the key from the Settings page, and it is never shown again. Read [DEPLOYMENT.md](DEPLOYMENT.md) before exposing the app to the internet.
- **Not security-reviewed by a third party.** The protections are tested (see [TESTING.md](TESTING.md) and [SECURITY.md](SECURITY.md), which also lists the known risks), but there has been no penetration test, no fuzzing and no automated scanner run.

## Fairness and privacy notes

- No personal data is collected beyond what a customer says in an order. Audio sent to Gnani is processed under Gnani's terms; read them before using real customers' voices.
- Recordings made by the Noise lab stay in browser memory and are sent only to your own server and, for a run, to Gnani.
